# 冲突提醒跟随20秒理解

用户要求冲突提醒依托现有每20秒整理的 Agent 结果。源码与生产交付分别记录如下；部署及安装不等于真实冲突质量验收。

## 行为

- 新正式会议的同场冲突复用原 Sol 增量整理调用，在同一个回包增加 `notice_ops`，不额外发逐句同场冲突请求。原跨往期会议的核对路径保留，正式场只向旧接口提供空的同场依据，并只接纳其他会议的历史依据；不会重复判断当前会议的同一对原话。只有有新增原话时整理，单轮串行；20秒是调度软目标，模型与手机读取仍有各自等待时间。
- 冲突必须有 `earlier_ids`、`current_ids` 两组确切原话，各1–3条，严格按来源顺序先后；当前依据含本轮实际处理原句且不能越过 `through`。模型先区分条件不同、预算明确更新、撤回、建议、引用与假设。内容均为待人核对的候选。
- 同一先前依据采用稳定提醒ID，后续变化更新原提醒；解除必须引用本轮明确的新依据。省略不代表解决。提醒最多30条，解除记录另有上限。达到上限时保留原提醒与原实时整理，安全省略的新候选数量单独标明，不因此暂停整场整理。
- 模型每轮至多2项提醒变化，与原整理变化合计仍受原6项（compact）及1400输出token预算约束。调用账本、未知暂停、防重、来源指纹和原保存合同保持。
- 旧依据从已覆盖会议的保留候选、开放/已解除提醒及小结检索原话。compact旧证据最多6句/1000字，提醒清单最多4项；没有读完整历史上下文，不保证任意20分钟前的限制都能进入本轮判断。`notice_context` 显示覆盖与省略数量。

## 接入

`scripts/live_minutes.py` 的成功checkpoint保存 `notice_protocol=sol-observer-v1`、`notice_evaluated`、`notice_context`、`attempt_id`及开放候选。旧草稿或缺少提醒判断的回包明确未记录，不以空数组冒充已判断无冲突。协议原有字段与旧checkpoint兼容。

`scripts/live_notices.py` 经主后端既有鉴权后的 `GET /v1/meetings/{sid}/live-notices` 只读投影当前有效结果。两边原话从当前原会议重读，不另存一份完整原话；回包前重核原始来源、本人修订/身份依据、保存合同、范围配置与checkpoint。GET不创建数据库、启动worker或调用模型。缺配置、来源失效或无法确认时返回明确状态并撤正文。pending可显示有效上版，结束后可只读保留。

真实部署需同时显式配置 `OOPS_LIVE_MINUTES_DB`、`OOPS_LIVE_MINUTES_CONFIG` 指向原worker账本及范围配置。主后端需能导入同版 `live_minutes.py` 与 `archive_policy.py`；生产现有worker和主后端分属不同源码目录，不能只复制路由便宣称已接通。配置仍只启用原获准的新正式会议范围，不补跑历史、已结束或失效记录。

网页 `public/funnel-live.js/css` 展示待核对冲突、问题及双方可定位的原话，无额外请求、跳页、声音或网页震动。

Android `OopsApi`/`HttpOopsApi` 新增同鉴权只读接口，`OopsEngine` 在活动正式会议每20秒读取原结果，替代正式会议的旧逐句冲突调用。`LiveAgentNotices` 校验模型、协议、成功版本、期限与本机原文/时间/有效说话人；本机来源修订代次防止旧回包复活。来源修订或核对未保存时先撤旧提醒；读取失败撤正文但保留已提醒ID及本人忽略状态，重连不重复震动。只有本场正在收音且原话仍近期的新稳定ID才提示，沿用原可关闭的短震动与冷却；更新/移除不震动。

Agent提醒正文不进入原会议提醒同步队列，避免已撤回的派生提醒留在另一份永久副本。原时间、跑题/议程和待办缺项路径未改，日常模式不提交到正式会议worker，不扩大五分钟内容保存范围。没有自动创建任务、交办Raft或代替本人确认。
