## 2. 会议完整记录与任务整理

完整转写归档与送给模型的分析输入是两个步骤。当前长会议缺陷主要发生在分析和合并阶段，不能据此说原始全文一定已被删掉；也不能以全文已存证明模型读完了全场。

### P1：长会议分析仍会删掉中段

`scripts/feishu_actions.py:484` 的 `transcript()` 默认限制 40,000 字符；`:503` 超限后只取前约三分之一、后约三分之二，中间替换成省略标记。`:613` 的正常纪要请求仍使用该默认值；三份独立生成都读取同一份截断输入。

影响：长会议中段的决定、待办和争议可能完全不进入模型。换用 Sol 或增加投票不能补回未输入的内容。

已保存的生产候选 `build/sol-production-20261016/stage/feishu_actions.py:531`、`:550`、`:648` 存在相同逻辑。此前 97 分钟专项回放绕过了截断，不代表正常会议链路已修。

建议：按模型实际输入预算完整分段分析并合并，保留原句 ID 与每段覆盖记录；超限应明确失败或标记未完整分析，不能静默省略中段。

### P1：多数投票会合并同句中的不同事项

`scripts/minutes_vote.py:24`–`:26` 仅凭共享任一句 ID 就认为是同一事项；`:72` 优先加入首个匹配组；`:82` 同分时保留第一份的措辞。

静态反例：原句 u1 含 A、B 两件不同任务，三份结果分别为 `[A(u1), B(u1)]`、`[B(u1)]`、`[B(u1)]`。后两份 B 都加入首份 A 的组，最终保留只出现一次的 A，反而丢失三份均提出的 B。待办、决定及待定事项都会受此匹配规则影响。

已保存的 Sol 生产候选 `minutes_vote.py` 同样存在。本轮仅推演分组逻辑，未执行测试。

建议：原句重叠只作为来源关联，事项合并还需区分具体命题；保留一条原话支持多件事项的能力。

### P1：清单中的零字节文件可能导致上传收尾 HTTP 500

服务端 `scripts/recordings.py:137` 接受 `size=0`；`manifest()` 只保存清单，不创建对应空文件。Android `RecordingUploader.kt:72` 对零长度文件不会发送任何分块。服务端 `complete():217` 将不存在文件的接收长度视为 0，随后 `:219` 调用 `_sha256()` 打开不存在文件，抛出 `FileNotFoundError`，进入通用 500。

SDK 异步连接失败可能经过正常停止和录音收尾保留空 PCM；该路径不经过同步启动抛错时的 `discard()`。历史文档也记录过无音频试连条目的上传 500，但生产当前 `recordings.py` 本轮未重新读取，不能宣称已复现线上故障。

建议：明确无真实音频的失败会话如何收尾；服务端对合法空文件及不合法空录音分别处理，不能接受清单后在完成阶段报内部错误。不自动删除用户历史队列。

### P2：部分纪要结果丢失可核对的原话来源

`scripts/feishu_actions.py:637`–`:640` 验证讨论要点引用后，只保留 topic／points，丢弃 ids。`:684`–`:688` 的 API 来源汇总也未纳入后续安排。Android `app.js:2558` 和 `:2560` 对讨论要点及后续跟进直接传空来源，所以手机无法从这些结果查看原话。

已保存的 Sol 生产候选存在相同处理。建议从生成清洗、投票、API 到手机入口完整保留引用；旧结果没有来源时如实提示，不能编造补齐。
